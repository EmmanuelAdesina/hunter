02 / EXECUTION MODEL

Five stages, one process

Every `hunter scan` invocation starts with a fresh process and a durable snapshot from the previous run.

01BOOTSTRAP

Load a trusted baseline

CLI flags and the strict profile are validated; enabled adapters and SMTP are wired. State loading replays a pending save journal and validates the material digest before scanning.

config → FileStore.Load → Snapshot
02DISCOVERY

Observe listing pages

The adapter pages through the public listing. The shared HTTP client applies timeouts, concurrency limits, request pacing, transient retries, and server Retry-After guidance.

Discover(ctx) → ProgramRef[]
03EVALUATION

Refresh only when needed

Listing changes, incomplete records, bootstrap, and staleness decide when details are fetched. The adapter parses status, access, scopes, rewards, and metadata into RawProgram; normalization standardizes tags and target types before fingerprinting. Catch-up reads are budgeted; event-driven reads are not.

ProgramRef → RawProgram → Program
04DECISION

Compare, gate, score

Normalized fields and stable fingerprints feed the diff engine. Parse trust and policy checks produce eligibility blockers; freshness and scoring rank opportunities but never override a failed hard gate.

diff → policy → freshness → triage
05COMMIT & DELIVER

Persist before sending

Programs, alert records, windows, and the material digest are saved through a recovery journal. New and pending alerts are then dispatched and acknowledged.

Save → pending merge → Dispatch → exit
03 / POLICY & ALERTING

Hard gates before attention

Eligibility is a policy result. Triage is a ranking signal. Alert triggers are a separate time- and evidence-bounded decision.

✓ POLICY ENGINE

Unknown is not approval

Access facts, lifecycle state, accepts-reports, in-scope surfaces, and crypto traits contribute structured checks. Any failed or unknown required check blocks eligibility unless the profile explicitly allows that unknown.

facts→checks→eligible / blocked
↗ ALERT GENERATOR

Evidence chooses the trigger

New launch age, newly eligible status, scope expansion, and material changes use their own configured trigger and recency window. Severity, eligibility, fingerprint idempotency, and the per-scan cap are applied before delivery.

trigger→window + severity→alert / suppress
i
Inventory is not approval.

The state store retains discovered program records for comparison and coverage. A saved program record does not mean it passed policy or generated an alert.

04 / STATE & RELIABILITY

Recoverable by design

The durable store is the scan’s memory. It supports change detection, coverage accounting, alert retries, and operator inspection.

STATE SURFACESFILE STORE
programs.jsonCurrent normalized program records and scan metadata
alerts.jsonRendered alert records and delivery acknowledgement state
windows.jsonOpportunity windows and competition evidence
history/<id>.jsonPer-program material-change history; appended separately
material.sha256Material-change marker used to detect snapshot inconsistency
.save-transaction.jsonWrite-ahead snapshot journal, removed after successful replay/save
R
SAVE PROTOCOL

Journal first.
Digest last.

  1. 01Persist complete transaction journal
  2. 02Replace programs, alerts, and windows
  3. 03Write material digest after snapshot files
  4. 04Remove journal; replay it on next load if interrupted
!
Notification delivery is at-least-once, not exactly-once.

The dispatcher records an attempt before sending and continues across the batch when one notification fails. If SMTP succeeds but saving the delivered marker fails, the pipeline still surfaces the bookkeeping error: delivered=1, failed=0, and the record stays retryable for a possible resend on a later scan.

05 / OPERATIONS

Run it, inspect it, trust it carefully

Production scheduling and CI are intentionally separate. The live worker reads the persisted state directory on every invocation.

⌁LIVE EXECUTION

systemd timer

deploy/systemd/hunter.timer launches the oneshot service on a five-minute cadence. The host persists the configured state directory between runs.

$ hunter scan --profile … --state …

06 / IMPLEMENTATION NOTES

Known seams in the current implementation

These are code-level observations, not product aspirations. Keep them visible until the behavior and configuration agree.

REVIEW ITEMS
A

program_states.alert_on_state is not wired

The YAML key is parsed and exposed by config, but no alert-generation path consumes it. Lifecycle reactivation may alert through the material-change path; this setting itself does not trigger it.

UNWIRED
B

Partial parse confidence currently passes the trust check

Low-confidence records are blocked by default. ConfidencePartial is treated as a pass at the parse-trust check; independent unknown access-gate checks can still block eligibility.

POLICY NUANCE
C

POC is not an eligibility gate

The current profile has no proof-of-concept acceptance rule, and the policy engine does not reject programs on POC status.

NOT CONFIGURED
D

Coverage “seen” is recorded after successful evaluation

A discovered reference that fails fetch/parse does not enter the current seen set, so that failure also contributes to coverage missing counts.
